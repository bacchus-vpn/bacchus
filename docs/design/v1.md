# Bacchus v1 design

This is the design of record. It supersedes the drifted research notes in
`vpn/_internal/design/` (kept, marked historical — see bottom of this doc) and
is read alongside `docs/threat-model.md`, which this plan is built to satisfy.

## Current architecture (as of 2026-07-02)

Bacchus is a Go mesh VPN: any node can be **client + relay + exit**
simultaneously (`-role client,relay,exit`). We build our own software — the
coordinator, node daemon, client, and protocol/routing/obfuscation logic are
all ours; we embed mature libraries (pion/WebRTC for DataChannels +
ICE/STUN/TURN NAT traversal) rather than gluing third-party apps or services
(rejected: Tailscale/Headscale, sing-box, AmneziaWG as external processes —
see ADR-0002 for the reasoning pattern this follows).

**Data path (proven end-to-end from Russia):**
```
client ──WebRTC (coordinator + STUN/TURN, NAT-traversal)──► [relay] ──► exit ──► internet
```
- **Coordinator** — UDP signaling / peer directory (ADR-0006). Never in the
  data path.
- **Node** — one binary, many roles; relays only forward, exits egress.
- **Direct-first** — client connects straight to an exit when reachable;
  relay is a fallback (and, once end-to-end encryption lands, a privacy
  option — see the E2E ADR).
- Confirmed working: RU client → our coordinator + STUN/TURN → a residential
  relay → our exit → internet, and direct client→exit over
  UDP/WebRTC.

**Repository layout** (single Go module, `bacchus` public monorepo +
`bacchus-payment` private stub — ADR-0002, ADR-0003):
`core/` (shared engine, currently mid-extraction — issue #7) · `bind/`
(gomobile facade, stub, deferred to v2 — ADR-0005) · `cmd/{node,coordinator,turn}`
· `clients/windows/` · `deploy/` (systemd, secrets from gitignored env files)
· `docs/`.

## Design corrections (from the 2026-07-02 review)

These corrections shaped how the v1 plan below is sequenced — each fixes a
specific wrong assumption carried over from the MVP-era notes:

1. **WebRTC is NAT traversal, not camouflage.** The MVP-era assumption that
   pion/WebRTC's DTLS "looks like WebRTC media" and is therefore
   censorship-resistant is wrong as a durable property: Snowflake, which uses
   exactly this approach, was fingerprinted and blocked in Russia. WebRTC
   stays as the first transport, but it lives **behind a pluggable Transport
   interface** (issue #10) so a second transport can ship without
   re-architecting, and its **DTLS fingerprint must be randomized** (issue
   #14) rather than trusted to blend in by default.
2. **The client must be full-device, not a browser proxy.** The current
   Windows client is a PAC/browser-scoped proxy. v1 requires **TUN-level
   routing + a fail-closed kill-switch + DNS handling** (issue #13) — a leak
   at the OS level defeats the threat model regardless of how good the
   transport is.
3. **Rendezvous cold-start is the make-or-break, not a solved problem.** A
   fresh RU client reaching a first contact with **no domain fronting**
   (Cloudflare is banned in Russia, so it cannot serve as a collateral-damage
   front for the bootstrap channel) is the hardest unproven step in the
   whole system (issue #18). Everything upstream of it (transport quality,
   client safety) is moot if cold-start doesn't work.
4. **Payments are a stub in v1, not a feature.** Real tokens, crypto payouts,
   and anti-fraud are v2. v1 ships **co-signed metering only** (issue #20) —
   enough to prove the accounting hook works, no payout logic.

## v1 plan — risk-sequenced milestones

The board (the pre-migration project board; see the tracker note in the README)
is sequenced by **risk**, not by architectural layer: the riskiest unknowns
are pulled earliest regardless of which component they touch. Milestones
ladder to v1; mobile, real payouts, and multi-platform clients are **v2:
deferred** (issue #4 and others explicitly tagged).

- **M0 — Foundations.** Nothing else is safe to build until these land:
  extract the engine into `core/` (#7), a protocol version/capability
  handshake (#8), this threat model (#9), the pluggable Transport interface
  (#10), and this design + ADR consolidation (#11).
- **M1 — Safe client.** The client must be safe before it's useful:
  end-to-end client↔exit encryption / onion property (#12), full-device TUN
  + DNS + fail-closed kill-switch (#13).
- **M2 — Transport coverage.** No single transport works everywhere in RU —
  confirmed by testing from a real RU vantage, since censorship there is
  decentralized and enforced per-operator: randomize the WebRTC/DTLS
  fingerprint (#14), add a second transport behind the interface — obfuscated
  UDP / Reality-XHTTP (#16), client-side transport pool + automatic per-user
  failover (#15), prefer peer-relay over TURN for the data plane (#17).
- **M3 — Rendezvous.** The real boss fight: cold-start bootstrap for a fresh
  RU client with no domain fronting (#18), app distribution into Russia
  (#19), coordinator pool + client rotation (#6).
- **M4 — Resilience and accounting.** Survive real use: auto-reconnect +
  relay failover (#2), idle session cleanup + stale-peer expiry (#3), a
  second exit so selection is real (#5), minimal co-signed metering stub, no
  payout (#20).

Completing M0–M4 is v1: a runnable service on our own infra, RU-reliable,
one platform pair, accounting stubbed. **v2 (deferred, issue #4 and
siblings):** mobile via the gomobile facade, real crypto payouts/tokens,
multi-platform clients (Mac/Android/iOS), a reachability map / decentralized
rendezvous.

## Non-goals for v1

Scope is deliberately narrow — see `docs/threat-model.md` Non-goals for the
security-relevant ones (not a global-passive-adversary defense, not
Tor-grade anonymity). Architecturally out of v1: multi-hop chaining beyond
client→relay→exit, a reachability map / smart routing, abuse handling and
ops hardening at scale, mobile clients, real payment rails.
