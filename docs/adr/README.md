# Architecture Decision Records

Short records of significant decisions. Format: **Status, Context, Decision,
Consequences**. Numbered sequentially; superseded records are kept and marked, not
deleted. New significant decisions ship as an ADR in the same PR (see ADR-0007).

## Reading the issue numbers in these records

**ADR numbers are stable and mean one thing. Issue numbers do not.** This project moved
trackers on **2026-07-28**, and every issue open on that day was re-filed with a new
number. References written before the move were left as they were, so `#N` in this
repository belongs to one of two schemes depending on when the sentence was written:

- **Records 0001–0042** arrived in this repository's initial commit. Their original
  bodies were written against the **retired** tracker, so a bare `#N` there is one of
  its numbers.
- **Records 0043 onward** were written here, against the **current** tracker.
- **Amendments appended to an earlier record** are the awkward case, and the reason the
  split is not simply "which file". An amendment introduces current numbers while still
  citing retired ones for the history it builds on, so one record — and sometimes one
  paragraph — carries both. ADR-0038's last amendment cites `#26` in the current scheme
  alongside three numbers in the retired one.

So the boundary runs between passages, not between files, and the two schemes are not
distinguishable by inspection. What tells them apart is the subject matter, not the
number.

**The practical consequence: a retired number below the current tracker's high-water
mark will autolink, and it will point somewhere unrelated.** A record citing `#42` for
admission gating produces a link to a relay-directory change; `#60` for end-to-end exit
verification produces a link to a coordinator-hosting change. So a link in these records
is only as trustworthy as the passage it sits in: where the link and the sentence
disagree, the sentence is right.

Three things worth knowing before trying to "fix" a number:

- **Most retired numbers have no current equivalent.** Only the issues still open on
  2026-07-28 were re-filed. Anything already closed — which is most of what these
  records cite — was not, so there is nothing to renumber it to.
- **`#76` is a label, not just a number.** It was the relay-chaining epic, and the
  current tracker's own issue titles still carry it: `[#76 §9-6] Chain-aware liveness
  and rebuild`, `[#76 §9-9] NAT-traversed intermediate hops`. `#76 §9-N` reads as a
  section of that design, and renumbering it here would desynchronize these records
  from live issue titles.
- **The retired tracker is gone, not merely private.** Its remotes are dead. The only
  surviving record of it is a workspace-local archive that is deliberately never
  published, so a retired number cannot be resolved by anyone outside the project — and
  in many cases the ADR text is now the better record of what the issue said.

The same two-scheme split runs through code comments and the rest of `docs/`, for the
same reason and with the same reading. Comments are inert — nothing autolinks inside a
`.go` file — but a number in one is no more resolvable than a number here.

**Writing a new reference:** a current issue is cited bare, as #77, so it links.
A retired one is cited as `` `old #157` `` — a code span, which GitHub cannot autolink,
so it can never point at an unrelated issue. See [CONVENTIONS.md](../../CONVENTIONS.md).

- [0049](0049-linux-privilege-boundary.md) — The Linux privilege boundary for #37 `[E10]`: enforcement splits across a process boundary, with `clients/fyne` unprivileged and a root helper (`bacchus-netd`) behind a `SO_PEERCRED`-gated unix socket owning all thirteen privileged `osNet` methods — chosen over file capabilities (an ambient grant, lost by `cp`/`nosuid`/upgrade, and exec-per-op leaves the rollback of a security boundary in the untrusted process, which is what `TestFailedBringUpOrphansNothing` pins) and over polkit (ADR-0030's auto-reconnect makes every failover a password prompt, and `allow_active=yes` buys a launcher rather than a boundary; polkit's real fit is a one-time install-time grant). Unlink rather than overwrite, stated honestly: rewriting bytes in place is not an erase on a journaling or CoW filesystem. **The daemon-consumes-a-file rival lost on its own seam** — the unlink is a second operation after the one that cannot be repeated, so a read-only filesystem reproduces exactly the outcome ADR-0056 refused; it also puts a network call on a forwarder's startup path and forces the daemon to decide what a claim-code file means beside an already-enrolled device, where neither deleting nor keeping it is right. An env var fixes the `/proc` exposure and none of the lifecycle; a second binary is a second thing the release channel must sign. **An account service with an empty `-device-cred-dir` is now a startup refusal**, before anything reaches the network, and so is a `-claim-code-file` on a start that will not read it (a silently inert flag is this record's subject one level up). `-enroll` with no code **collects** instead, spending nothing — the way back for a node that lost its credential and kept its key, which `devicestore`'s deliberate asymmetry (key hard-fails, credential soft-fails to empty) makes reachable; a one-shot rather than an automatic startup call, because `bad_assertion` counts toward a per-device-key cooldown and a crash loop would spend it. **Renewal ships with it** as ADR-0046 §6 ruled, through the same `core/accountclient` **unchanged** — a second embedder, not a second implementation, and the dependency still runs one way only. En route it corrects the check that argument is usually written with: ADR-0056 §2's "`go list -deps ./core` names no HTTP client" is false and was false when written, because `core` imports utls directly and utls reaches `net/http` through brotli — the property holds, the absolute form of the check does not measure it, and the diff form does (`#239`). A failing renewal escalates **on the clock** rather than on what went wrong, at 3h against `core`'s 6h margin, because the margin is when a node starts trying and a warning at the last retry lands where nobody can act on it; a lapsed subscription and a revoked device ignore the clock. En route it fixes a rollback bug it did not cause: a one-shot must not run ADR-0069's startup demotion check, because `CheckStartup` CLAIMS the probation and only the serving path clears it — `-list` already consumed it on a freshly applied release, so the next real start found `started=true` and demoted a build nothing had tried, and `-enroll` would have been a likelier second instance since provisioning follows deployment (`#240` holds the missing regression test).
