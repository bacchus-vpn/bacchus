# Architecture Decision Records

Short records of significant decisions. Format: **Status, Context, Decision,
Consequences**. Numbered sequentially; superseded records are kept and marked, not
deleted. New significant decisions ship as an ADR in the same PR (see ADR-0007).

## Reading the issue numbers in these records

**ADR numbers are stable and mean one thing. Issue numbers do not.** This project moved
trackers on **2026-07-28**, and every issue open on that day was re-filed with a new
number. References written before the move were left as they were, so `#N` in this
repository belongs to one of two schemes depending on when the sentence was written:

- **Records 0001–0042** arrived in this repository's initial commit. Their original
  bodies were written against the **retired** tracker, so a bare `#N` there is one of
  its numbers.
- **Records 0043 onward** were written here, against the **current** tracker.
- **Amendments appended to an earlier record** are the awkward case, and the reason the
  split is not simply "which file". An amendment introduces current numbers while still
  citing retired ones for the history it builds on, so one record — and sometimes one
  paragraph — carries both. ADR-0038's last amendment cites `#26` in the current scheme
  alongside three numbers in the retired one.

So the boundary runs between passages, not between files, and the two schemes are not
distinguishable by inspection. What tells them apart is the subject matter, not the
number.

**The practical consequence: a retired number below the current tracker's high-water
mark will autolink, and it will point somewhere unrelated.** A record citing `#42` for
admission gating produces a link to a relay-directory change; `#60` for end-to-end exit
verification produces a link to a coordinator-hosting change. So a link in these records
is only as trustworthy as the passage it sits in: where the link and the sentence
disagree, the sentence is right.

Three things worth knowing before trying to "fix" a number:

- **Most retired numbers have no current equivalent.** Only the issues still open on
  2026-07-28 were re-filed. Anything already closed — which is most of what these
  records cite — was not, so there is nothing to renumber it to.
- **`#76` is a label, not just a number.** It was the relay-chaining epic, and the
  current tracker's own issue titles still carry it: `[#76 §9-6] Chain-aware liveness
  and rebuild`, `[#76 §9-9] NAT-traversed intermediate hops`. `#76 §9-N` reads as a
  section of that design, and renumbering it here would desynchronize these records
  from live issue titles.
- **The retired tracker is gone, not merely private.** Its remotes are dead. The only
  surviving record of it is a workspace-local archive that is deliberately never
  published, so a retired number cannot be resolved by anyone outside the project — and
  in many cases the ADR text is now the better record of what the issue said.

The same two-scheme split runs through code comments and the rest of `docs/`, for the
same reason and with the same reading. Comments are inert — nothing autolinks inside a
`.go` file — but a number in one is no more resolvable than a number here.

**Writing a new reference:** a current issue is cited bare, as #77, so it links.
A retired one is cited as `` `old #157` `` — a code span, which GitHub cannot autolink,
so it can never point at an unrelated issue. See [CONVENTIONS.md](../../CONVENTIONS.md).

- [0049](0049-linux-privilege-boundary.md) — The Linux privilege boundary for #37 `[E10]`: enforcement splits across a process boundary, with `clients/fyne` unprivileged and a root helper (`bacchus-netd`) behind a `SO_PEERCRED`-gated unix socket owning all thirteen privileged `osNet` methods — chosen over file capabilities (an ambient grant, lost by `cp`/`nosuid`/upgrade, and exec-per-op leaves the rollback of a security boundary in the untrusted process, which is what `TestFailedBringUpOrphansNothing` pins) and over polkit (ADR-0030's auto-reconnect makes every failover a password prompt, and `allow_active=yes` buys a launcher rather than a boundary; polkit's real fit is a one-time install-time grant). The decisive argument is the TUN descriptor: the netstack runs in the client process, and a unix socket is the only one of the three that can pass an fd — the vendored wireguard-go already splits exactly there, `CreateTUN` doing the privileged `open`+`TUNSETIFF` and `CreateTUNFromFile` doing only unprivileged work on a descriptor it is handed. The helper speaks netlink and nftables directly and never shells out, so no client string can become an instruction; only prefixes, an address and a session token cross inward, while interface names and `gatewayInfo` are derived helper-side and cross outward only (verified: `osn.defaultGateway` is the package's sole producer — `tunnel.go:79`, `poolroutes.go:114`/`:230`). The security claim is stated without inflation: a compromised GUI can leak traffic and lift the kill-switch, because the GUI is what decides policy, but cannot become root, touch state outside the helper's own table, or persist past a reboot — compromise costs the VPN, not the machine, and the kill-switch is consequently no defence against local malware. Corrects the card on two points: the split-tunnel "mechanism decision" (routing rules / cgroup v2 / netns) **is not open** — `splittunnel.go` is destination-based, portable and shipped, its only decision function takes an IP, and ADR-0025 already ruled per-app split tunnelling out of scope, so what remains is three route methods and nothing to decide; and DNS is where `osNet` is genuinely short a primitive, since systemd-resolved's `127.0.0.53` stub is loopback that **no** route can capture (the kernel's `local` table precedes `main`), which breaks bypass-domain learning and gives a leak with the kill-switch off or total DNS failure with it armed. Records the full mechanism/privilege map for all fourteen methods, that `refreshKillSwitchAllowIP` has no fails-closed window on Linux (nftables named sets take an atomic element add, so ADR-0025's remove-and-recreate must not be ported), and that `tunnel_test.go`'s five pinned orderings are inherited structurally rather than re-established — so the helper must execute primitives and never own bring-up order — with a user+network namespace giving #37 the real-kernel, unprivileged CI verification #59 never had (a netns as test harness, explicitly not as split-tunnel mechanism). - [0050](0050-macos-tunnel-mechanism.md) — The macOS tunnel mechanism for #36 `[E9]`: a `NEPacketTunnelProvider` in a Developer ID **system extension**, rejecting the privileged-helper-plus-`utun` route that ADR-0049 chose for Linux — so the two Unix platforms deliberately diverge.
